# درگاه زیبال برای LifterLMS

این افزونه درگاه پرداخت زیبال را به LifterLMS اضافه می‌کند و پرداخت یک‌باره، دوره آزمایشی و پرداخت‌های دوره‌ای را پوشش می‌دهد. پرداخت دوره‌ای در این نسخه به‌صورت دستی انجام می‌شود؛ یعنی افزونه در سررسید هر قسط، سفارش را در انتظار پرداخت قرار می‌دهد و کاربر همان قسط را از صفحه سفارش پرداخت می‌کند.

## پیش‌نیازها

- وردپرس 5.8 یا جدیدتر
- PHP 7.4 یا جدیدتر
- LifterLMS 6.0 یا جدیدتر
- مرچنت‌کد فعال زیبال برای حالت واقعی

حداقل نسخه LifterLMS روی 6.0 قرار گرفته است. دلیل آن هوک `llms_view_order_after_secondary` است که دکمه «پرداخت قسط با زیبال» روی آن رندر می‌شود و از نسخه 6.0.0 به LifterLMS اضافه شده است. روی نسخه‌های قدیمی‌تر این دکمه نمایش داده نمی‌شود و قسط سررسیدشده راهی برای پرداخت ندارد.

## قابلیت‌ها

- پرداخت یک‌باره دوره‌ها و عضویت‌ها
- پرداخت دوره‌ای ماهانه، سالانه یا بازه‌های تعریف‌شده در پلن
- پشتیبانی از تعداد اقساط محدود و پرداخت‌های بدون تاریخ پایان
- دوره آزمایشی رایگان یا پولی
- یک درخواست، شناسه محلی و توکن callback مستقل برای هر نوبت پرداخت
- بررسی سروربه‌سرور پرداخت با `verify`
- استفاده از `inquiry` برای تعیین تکلیف پاسخ‌های مبهم یا در انتظار
- حالت آزمایشی زیبال با مرچنت `zibal`
- ثبت متن دقیق خطای زیبال در یادداشت سفارش و جعبه مدیریت
- نمایش پیام عمومی و امن به خریدار

## پرداخت دوره‌ای چطور انجام می‌شود؟

این درگاه از کارت کاربر برداشت خودکار انجام نمی‌دهد. در زمان سررسید، افزونه سفارش را روی `On Hold` می‌گذارد. کاربر وارد صفحه سفارش می‌شود و با دکمه «پرداخت قسط با زیبال» به درگاه می‌رود. بعد از تأیید موفق زیبال، `LLMS_Controller_Orders::transaction_succeeded()` سفارش را دوباره `Active` می‌کند و موعد بعدی را زمان‌بندی می‌کند.

هر قسط یک تلاش پرداخت جدا دارد. `trackId`، مبلغ، نوع پرداخت، محیط آزمایشی یا واقعی، شناسه سفارش زیبال و توکن callback در همان تلاش ذخیره می‌شوند. بنابراین callback یک قسط نمی‌تواند به قسط دیگر یا سفارش دیگری متصل شود.

در زمان سررسید دسترسی دانشجو تا پرداخت قسط متوقف می‌شود. وضعیت `On Hold` در LifterLMS یک وضعیت خطاست: هوک `lifterlms_order_status_on-hold` متد `LLMS_Controller_Orders::error_order()` را اجرا می‌کند که زمان‌بندی پرداخت دوره‌ای را حذف و دانشجو را با تریگر `cancelled` از دوره خارج می‌کند. با پرداخت موفق قسط، هر دو مورد دوباره برقرار می‌شوند.

LifterLMS اعلان آماده‌ای برای «قسط سررسیدشده» ندارد. افزونه در این لحظه یادداشت سفارش ثبت می‌کند و اکشن زیر را اجرا می‌کند تا سایت بتواند اعلان دلخواه خودش را بفرستد:

```text
do_action( 'llms_manual_payment_due', $order, $gateway );
```

## دوره آزمایشی

اگر دوره آزمایشی رایگان باشد، افزونه بدون فرستادن کاربر به زیبال یک تراکنش صفر با نوع `trial` ثبت می‌کند و زمان‌بندی پرداخت بعدی را به LifterLMS می‌سپارد.

اگر دوره آزمایشی مبلغ داشته باشد، فقط مبلغ همان دوره آزمایشی به زیبال ارسال می‌شود. پرداخت‌های بعدی با مبلغ عادی پلن و به‌صورت قسط مستقل انجام می‌شوند.

## نصب و تنظیم

1. پوشه افزونه را در `wp-content/plugins` قرار دهید و افزونه را فعال کنید.
2. در تنظیمات پرداخت LifterLMS، درگاه زیبال را فعال کنید.
3. برای حالت واقعی، مرچنت‌کد زیبال را وارد کنید.
4. واحد مبلغ را انتخاب کنید. در بیشتر سایت‌ها گزینه «تشخیص خودکار» مناسب است.
5. برای تست بدون مرچنت واقعی، حالت آزمایشی درگاه را فعال کنید.

حالت آزمایشی و واقعی از هم جدا هستند. پرداختی که در حالت آزمایشی ایجاد شده باشد در حالت واقعی تأیید نمی‌شود و برعکس.

## مبلغ و واحد پول

زیبال مبلغ را به ریال دریافت می‌کند. اگر قیمت‌های LifterLMS با تومان ذخیره شده باشند، افزونه مبلغ را پیش از ارسال در ۱۰ ضرب می‌کند. واحدهای شناخته‌شده `IRR`، `IRT` و `TOMAN` هستند.

طبق محدودیت درگاه، مبلغ باید بیشتر از ۱۰۰۰ ریال باشد. مبلغ نامعتبر، اعشاری یا ارزی که افزونه نتواند تشخیص دهد پیش از ساخت درخواست رد می‌شود.

اگر مرچنت‌کد وارد نشده باشد یا واحد پول فروشگاه پشتیبانی نشود، درگاه زیبال از طریق `can_process_access_plan()` اصلاً در صفحه پرداخت نمایش داده نمی‌شود تا کاربر بعد از انتخاب درگاه با خطا روبه‌رو نشود. این فیلترکردن به LifterLMS 7.5 یا جدیدتر نیاز دارد؛ روی نسخه‌های پایین‌تر درگاه نمایش داده می‌شود و خطا در زمان ساخت درخواست گرفته می‌شود.

برای سفارشی‌سازی کنترل‌شده می‌توان از فیلترهای زیر استفاده کرد:

```text
llms_zibal_gateway_amount
llms_zibal_supported_currencies
```

## کنترل پرداخت

مسیر عادی یک پرداخت به این شکل است:

```text
ساخت تلاش محلی → درخواست زیبال → انتقال کاربر → callback
→ verify سروربه‌سرور → inquiry در پاسخ مبهم → ثبت تراکنش
→ تکمیل یا فعال‌شدن سفارش → زمان‌بندی موعد بعدی
```

افزونه پیش از انتقال کاربر، اطلاعات تلاش را در سفارش ذخیره و دوباره از دیتابیس می‌خواند. در callback، موارد زیر با اطلاعات همان تلاش تطبیق داده می‌شوند:

- `trackId`
- شناسه یکتای سفارش ارسال‌شده به زیبال
- مبلغ
- توکن callback
- کلید سفارش
- مرچنت و محیط آزمایشی یا واقعی
- نوع پرداخت: `single`، `trial` یا `recurring`

اگر پاسخ `verify` قطعی نباشد، افزونه از `inquiry` کمک می‌گیرد. پرداخت فقط وقتی نهایی می‌شود که نتیجه قطعی پرداخت‌شده و تأییدشده باشد.

سه حالت از هم تفکیک می‌شوند:

- **ناموفق:** وضعیت‌های قطعی زیبال مثل لغو توسط کاربر، موجودی ناکافی یا رمز اشتباه. همچنین وضعیت `-1` (در انتظار پرداخت) وقتی callback هم `success=0` فرستاده باشد؛ یعنی کاربر صفحه درگاه را رها یا لغو کرده است. این حالت رایج‌ترین مسیر ناموفق است و فقط سفارش را ناموفق می‌کند، نه بیشتر.
- **نیازمند بررسی:** پاسخ‌های واقعاً متناقض. مثلاً وضعیت `2` (پرداخت‌شده و تأییدنشده) یا وضعیت `-1` در حالی که callback ادعای `success=1` کرده است.
- **موفق:** فقط نتیجه `100` و وضعیت `1`.

این تفکیک عمدی است. اگر رهاکردن درگاه هم «نیازمند بررسی» حساب شود، سفارش روی `On Hold` می‌رود و طبق `error_order()` دانشجو از دوره خارج و زمان‌بندی پرداخت دوره‌ای حذف می‌شود — برای پرداختی که اصلاً انجام نشده.

قابلیت `Lazy` زیبال در این افزونه استفاده نشده است. در Lazy، تأیید تراکنش به عهده پذیرنده است و اگر ظرف ۲۰ دقیقه `verify` ارسال نشود مبلغ خودکار به کارت پرداخت‌کننده برمی‌گردد. ضمناً callback آن به‌جای Query String به‌صورت `POST` و با بدنه JSON می‌آید. این مسیر برای پرداخت دوره‌ای دستی سود روشنی ندارد و ریسک برگشت ناخواسته اضافه می‌کند.

## خطاها و اطلاعات مدیریتی

متن دقیق خطای زیبال همراه با مرحله و کد نتیجه در یادداشت سفارش ثبت می‌شود و در جعبه «جزئیات پرداخت زیبال» داخل مدیریت سفارش قابل مشاهده است. این اطلاعات برای پیگیری پشتیبانی است.

به خریدار جزئیات داخلی زیبال، پاسخ خام API یا اطلاعات فنی نمایش داده نمی‌شود. کاربر فقط یک پیام عمومی دریافت می‌کند و نتیجه کامل برای مدیر و پشتیبانی داخل سفارش باقی می‌ماند.

در پرداخت موفق، `trackId`، `refNumber`، `paidAt` و شماره کارت ماسک‌شده، در صورت وجود، ثبت می‌شوند.

## شناسه درخواست‌ها و User-Agent

تمام درخواست‌های `request`، `verify` و `inquiry` با هدرهای زیر ارسال می‌شوند:

```text
User-Agent: Zibal-WordPress-LifterLMS/2.4.0 (WordPress/…; LifterLMS/…; PHP/…)
X-Zibal-Plugin: wordpress-lifterlms/2.4.0
```

آدرس سایت، مسیر صفحه و اطلاعات مشتری داخل User-Agent قرار نمی‌گیرد. برای تغییر کنترل‌شده آن می‌توان از فیلتر `llms_zibal_user_agent` استفاده کرد.

زیبال برای شروع تراکنش به دامنه و Referer صحیح نیاز دارد. روی صفحه‌ای که کاربر را به درگاه می‌فرستد، سیاست `Referrer-Policy: no-referrer` نگذارید و دامنه سایت را در پنل زیبال درست ثبت کنید.

## مواردی که عمداً پشتیبانی نمی‌شوند

- برداشت خودکار از کارت یا حساب کاربر
- ذخیره کارت یا توکن پرداخت
- تلاش خودکار دوباره پس از شکست قسط
- استرداد وجه از طریق API این افزونه
- تغییر مبلغ یا برنامه اقساط یک سفارش فعال
- متد `Lazy`
- ارسال `mobile` و `nationalCode` خریدار به زیبال
- `checkMobileWithCard` و `allowedCards`
- تسهیم: `multiplexingInfos`، `percentMode` و `feeMode`

API درگاه اینترنتی زیبال endpoint عمومی برای برداشت خودکار، ذخیره کارت یا ساخت بازپرداخت ارائه نمی‌کند. به همین دلیل این موارد با یک پرداخت عادی شبیه‌سازی نشده‌اند.

باقی موارد این فهرست در API زیبال وجود دارند اما عمداً پیاده نشده‌اند: یا داده هویتی خریدار (موبایل و کد ملی) را وارد جریان پرداخت می‌کنند، یا به پیکربندی اختصاصی حساب پذیرنده (شبا و شناسه ذی‌نفع) نیاز دارند که جای آن در این افزونه نیست. درخواست پرداخت فقط `merchant`، `amount`، `callbackUrl`، `orderId` و `description` را می‌فرستد.

## نمایش نتیجه در صفحه

callback معتبر به‌صورت خودکار پردازش می‌شود. برای نمایش نتیجه پرداخت در محل دلخواه می‌توانید از شورت‌کد زیر استفاده کنید:

```text
[llms_zibal_payment_result]
```

اطلاعات نتیجه فقط برای صاحب سفارش یا مدیر سایت قابل مشاهده است.

## کنترل‌های امنیتی

- توکن تصادفی مستقل برای callback هر تلاش
- شناسه یکتای متفاوت برای هر درخواست زیبال
- قفل جدا برای ساخت درخواست و تأیید callback
- پردازش تکرارپذیر و جلوگیری از ثبت دوباره یک پرداخت
- تطبیق مبلغ و شناسه‌های پاسخ با اطلاعات محلی
- تفکیک کامل حالت آزمایشی و واقعی
- پنهان‌ماندن درگاه وقتی مرچنت یا واحد پول معتبر نیست
- توقف امن در پاسخ‌های مبهم و انتقال به بررسی دستی
- بررسی کد HTTP، ساختار JSON و timeout درخواست‌ها
- استفاده از اعتبارسنجی TLS پیش‌فرض وردپرس

## توسعه و تست

دستورهای بررسی محلی:

```bash
php -l lifterlms-gateway-zibal.php
php -l includes/class.llms.payment.gateway.zibal.php
php tests/security-smoke.php
```

پوشه `tests`، فایل‌های گزارش بررسی، ZIPهای خروجی و تنظیمات محلی Git جزو بسته انتشار نیستند و نباید روی مخزن عمومی قرار بگیرند. فایل `.gitignore` محلی نیز در این پروژه برای دنبال‌نشدن این موارد استفاده می‌شود.

اجرای تست محلی جای پرداخت واقعی آزمایشی روی یک سایت staging را نمی‌گیرد. پیش از انتشار عمومی، یک پرداخت یک‌باره، یک دوره آزمایشی و حداقل دو قسط متوالی را با callback واقعی بررسی کنید.
